# Engineering Standards

## Tooling
- Python >=3.12, **uv** for environment, dependency management and reproducible lockfile (`uv.lock`).
- Use `uv sync`, `uv run` and `uv add`; do not introduce Poetry/Pipenv or manually modify lockfile.
- FastAPI, Pydantic v2, SQLAlchemy 2.0 async, Alembic, psycopg3, pytest, pytest-asyncio, Ruff. Add dependencies as features need them.
- TypeScript/React for frontend; package manager chosen once the frontend is created; avoid mixing managers.

## Proposed module structure (create incrementally)
```text
backend/
  src/forexbot/{api,core,db,models,schemas,repositories,services,workers,integrations}/
  alembic/  tests/  pyproject.toml
mt5-gateway/{src,tests}/
frontend/{src,package.json}
infra/   docs/   tasks/
```
Existing single-package uv scaffold is fine until a deliberate migration; do not restructure without a concrete reason and tests.

## Code rules
- Explicit typing and descriptive naming; no giant service classes or circular dependencies.
- Make parsers and risk calculators pure where possible; external clients behind interfaces, adapters in `integrations/`.
- API layer validates auth/input, delegates to service; no inline SQL or order submission in routers.
- Async DB sessions are request/task-scoped; never share a session across concurrent tasks.
- Use `Decimal` for money/prices/volume and PostgreSQL `NUMERIC`; never compare forex prices with binary float equality.
- Store UTC timezone-aware timestamps; display configurable user/broker timezone. Define cutoffs for daily reset.
- Prefer meaningful SQL unique constraints, transaction boundaries, and explicit row locks for concurrent order admission.
- Structured logs include `correlation_id`, signal ID, stage and reason; redact secrets/personal identifiers.
- Version external contracts and signal/risk policy revisions; fail clearly on breaking changes.
- Keep dependencies current but add only when needed, and confirm actual tool versions in the repo.

## Checks when implemented
```bash
uv sync
uv run ruff check .
uv run ruff format --check .
uv run pytest -q
```
Do not assume any command exists until inspecting project configuration. When a check is absent, report it as not configured.

## Migration protocol
1. Design entity/constraint and indexes in `docs/DATABASE_SCHEMA.md`.
2. Create forward Alembic migration; review autogenerated operations manually.
3. Test upgrade/downgrade on nonproduction disposable PostgreSQL.
4. Never run destructive migrations against live Neon data without backup, impact review and approval.

## Git workflow
- Short feature branches, one scoped task per PR, conventional commit messages where practical.
- Avoid force-push to main; no secrets or environment-specific configs.
- PR description includes scope, screenshots for UI, migration changes, checks, and trading-safety assessment.
